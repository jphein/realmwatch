# HP V1910-24G Switch Runbook

The single Comware-firmware switch in the realm. Sits at `10.0.6.103` on VLAN6.
Everything else (APs, firewall, backup router) runs OpenWrt. This runbook
captures the V1910-specific quirks discovered during the **2026-04-28 trunk
audit**, the access pattern (hidden cmdline-mode), and the canonical port
configuration we converged on.

## Quirks worth knowing

1. **`admin` does not get exec privileges by default.** Even though the user
   is level 3 in the local-user database, SSH lands you in level 0 ("Visit"
   mode) — only display commands work. To get `system-view`, `interface`,
   `save`, etc. you must enter the **hidden cmdline-mode** with vendor
   password `512900` (yes, really):

   ```
   <HP> _cmdline-mode on
   All commands can be displayed and executed. Continue? [Y/N] Y
   Please input password: 512900
   <HP>
   ```

   This is per-VTY-session — every new SSH connection requires the unlock.

2. **Some `display` syntaxes differ from mainline Comware.** `display vlan
   brief` is rejected; use `display vlan all`. `display port` alone is
   incomplete; use `display port hybrid` or `display port trunk`.

3. **All ports default to `link-type hybrid`.** Hybrid (HP terminology)
   = Cisco-style trunk that can also carry one or more *untagged* VLANs.
   This is more permissive than `access` or `trunk` modes — it's also
   easier to misconfigure. See "Trunk normalization" below.

4. **Comware requires the PVID's VLAN to be in the port's allowed list.**
   You can't `port hybrid pvid vlan 1` if VLAN1 was previously removed
   with `undo port hybrid vlan 1`. Re-add it (`port hybrid vlan 1
   untagged`) first, then change PVID.

5. **LLDP is globally disabled by default.** Per-interface LLDP is enabled
   from the factory but the global flag is off. Both must be on for
   `display lldp neighbor-information` to populate. Enable globally:
   `system-view ; lldp enable`.

6. **No SFTP server.** File transfer requires `xmodem` / `tftp` /
   `ftp` — there's no SCP. We don't usually need to push files to it.

## Connecting

The full SSH incantation, including ciphers the V1910's old SSH server
expects:

```bash
sshpass -p "$PASS" ssh -tt \
    -o StrictHostKeyChecking=no \
    -o KexAlgorithms=+diffie-hellman-group-exchange-sha1 \
    -o Ciphers=+aes128-cbc \
    -o HostKeyAlgorithms=+ssh-rsa \
    -o PubkeyAuthentication=no \
    admin@10.0.6.103
```

For automation use the expect scripts under `scripts/switch/`. They handle
the cmdline-mode unlock automatically.

## Operational scripts

Located in `scripts/switch/`. Require `expect`, `sshpass`, `bw` (Bitwarden
CLI). All log full output to stdout — pipe to a file for archival.

```bash
sudo apt install expect sshpass
# bw is already installed via npm (~/.npm-global/bin/bw)
```

| Script | Purpose |
|---|---|
| `switch-audit.exp` | Capture full state: `display vlan all`, `display port hybrid`, `display current-configuration`, MAC table, LLDP neighbors. Read-only. Run any time. |
| `switch-apply-vlan-normalize.exp` | One-shot: normalize ports 15-28 to PVID=1, untagged VLAN1, all real VLANs (3-12, 20, 38) tagged. Idempotent — safe to re-run. Includes `save force`. |
| `switch-enable-lldp.exp` | Enable LLDP globally + save. Idempotent. |

### Credentials

The admin password is **fetched from the Bitwarden vault at runtime** (item
name: `HP Switch 10.0.6.103`, username `admin`). The vault must be
unlocked before running any script:

```bash
bw status        # check; expect "unlocked"
bw unlock        # if locked — outputs an export line for $BW_SESSION
```

The cmdline-mode unlock string `512900` is the public HP V1910 service
code — documented on HP support forums for over a decade. It's left
inline in the scripts. The only real secret is the admin password.

Each script uses `sshpass -e` (reads from `$SSHPASS` env var) instead of
`sshpass -p` so the password isn't visible in `ps` output.

## Trunk normalization (2026-04-28)

### What was wrong

Before the audit, ports GE1/0/15-28 were configured as **hybrid trunks with
the IoT VLAN (10) untagged**. The DHCP-OFFER drop pattern for clients on
the `jplovescl` SSID (and any other VLAN10 SSID) traced to this:

1. Client on AP joins jplovescl → AP sends DHCPDISCOVER tagged VLAN10 to switch.
2. Switch floods DHCPDISCOVER on VLAN10 → reaches gatekeeper, which sends OFFER.
3. Switch floods OFFER on VLAN10 ports — **but with VLAN10 marked
   "untagged" on the AP-facing port, the OFFER egresses untagged.**
4. The AP's WAN-facing trunk only accepts tagged VLAN10 frames for the
   jplovescl SSID; untagged frames go to the AP's management bridge and
   get dropped (no SSID matches).
5. Client never sees its OFFER → DHCP loops forever.

VLAN8 (iot) had every port tagged with no untagged egress anywhere, which
is why migrating SSIDs from VLAN10 → VLAN8 fixed the symptom yesterday.

### The fix (already applied)

For every "trunk" port (GE1/0/15..28):

- PVID **1** (Comware default).
- **VLAN1 added as untagged** — so `pvid 1` is allowed and any stray
  untagged frame dead-ends on VLAN1 (which has no other ports → silent drop).
- **VLAN3-12, 20, 38 all tagged** — every real VLAN is on every trunk.

Equivalent CLI for one port:

```
system-view
interface GigabitEthernet1/0/15
 port hybrid vlan 1 untagged
 port hybrid pvid vlan 1
 port hybrid vlan 3 to 12 20 38 tagged
 quit
quit
save force
```

The full apply is in `scripts/switch/switch-apply-vlan-normalize.exp`.

### Why PVID=1 instead of admin (VLAN6)

VLAN1 has zero other ports on this switch — anything tagged with VLAN1 by
the PVID dead-ends silently. That's safer than VLAN6 (admin), which would
leak stray untagged frames into the management VLAN. APs and Linux hosts
on these trunks emit only tagged frames anyway, so the PVID never gets
hit in normal operation.


## Backup and restore

Before any config change, capture the running config off-switch:

```bash
./switch-audit.exp > "/tmp/v1910-$(date +%F).log"
```

The full `display current-configuration` output is in that log. The V1910
has no `commit` / rollback workflow; `save force` is the only persistence.
To revert, you'd manually replay the prior config from the saved log
(use `system-view` + the per-port commands extracted from the backup).
